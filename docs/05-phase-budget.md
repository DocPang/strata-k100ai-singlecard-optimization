# 05 · 阶段耗时预算与硬件上限

## 硬件口径（实测，非手册值）

| 项 | 值 | 来源 |
|---|---|---|
| 设备 | 海光 K100_AI，gfx928，120 CU @ 1.400 GHz | `rocminfo` |
| bf16 峰值 | **165.3 TFLOP/s** | 120 CU × 1.4 GHz × 1024 FLOP/CU/clk |
| int8 峰值 | **330.8 TFLOP/s** | 同上 ×2 |
| int8 实测可达 | **330.07 TFLOP/s = 99.8%** | 纯寄存器 MMAC（NACC=8, grid=1920） |
| 可达条件 | ≥4 waves/SIMD 且 ≥8 个累加器 | 同上的参数扫描 |

> 注意：硬件**不是**瓶颈。瓶颈全部在"如何为业务形状把 int8 组织起来"。

## prefill 阶段预算（ctx128，总 ≈ 60.2–61.3 s）

| 阶段 | 耗时 (ms) | 占比 | 状态 |
|---|---|---|---|
| gate/up（MoE） | 10,735 – 10,801 | **17.5%** | 已关闭（9 条路径证伪，理论上限 −4%） |
| dense GEMM 池 | ≈ 16,600 | **27%** | 已关闭（见下） |
| qsa attn | 7,807 | 12.8% | 已关闭 |
| gdn recurrence | 6,672 | 10.9% | 已关闭 |
| hc read | 5,566 – 5,603 | 9.1% | 已关闭（引擎内 0%） |
| qsa select | 4,736 | 7.7% | 已关闭 |

## dense GEMM 池的形状归因（`STRATA_GEMM_ATTR=1`）

2944 次调用，合计 **21,244 ms**：

| 形状 (N×K) | 耗时 (ms) | 占比 |
|---|---|---|
| 2560 × 6144 | 6,798 | 32.0% |
| 10240 × 2560 | 6,469 | 30.4% |
| 6144 × 2560 | 3,538 | 16.6% |
| 12288 × 2560 | 2,245 | 10.6% |
| 合计 | 19,050 | **89.7%** |

其中 dequant 只占 **1.8%**（82.2 vs 4,614.1 ms）→ 缓存 dequant 收益上限 ≈0。

## 为什么"dense 池 27%"吃不到

rocBLAS f16 在这颗芯片上的实际天花板是 **60–70 TF/s（bf16 峰值的 36–42%）**，而**引擎内**同一调用已达 **95.6 TF/s**（比任何独立 microbench 都快）。也就是说引擎已经跑在这条路径的最优点上，剩下 27% 的时间是"必须要花的"。

要突破只能换成 int8 内核 —— 而 int8 内核需要 Tensile 级自动生成，见 [`07-int8-next-steps.md`](07-int8-next-steps.md)。
