# 07 · 下一步：把 int8 硬件真正吃满（Tensile / rocBLAS int8 适配）

## 问题陈述

| 事实 | 数据 |
|---|---|
| int8 硬件能力 | **330.07 TFLOP/s = 99.8% 峰值**（纯寄存器 MMAC 实测） |
| 业务形状上的 rocBLAS f16 天花板 | **60–70 TF/s**（= bf16 峰值的 36–42%） |
| 引擎内实际达成 | **95.6 TF/s**（已经比独立 microbench 快） |
| 自研 int8 GEMM 最好成绩 | **49.25 TF/s**（三阶段流水），比 rocBLAS f16 慢 2 倍 |

**结论：瓶颈不是硬件，也不是"再调一个 tile"，而是"为这颗芯片的 int8 参数空间做大规模自动搜索"。**

## Tensile 是什么

`rocBLAS` 背后的**内核生成器**：

1. 给定 (dtype, 架构, 形状)，枚举 tile 尺寸、LDS 布局、流水线深度、prefetch、寄存器分块、指令调度；
2. 生成**成千上万**个 kernel 变体（汇编级）；
3. 离线实测后编成 **solution 表**（`logic.yaml` + `.s` + 编号）；
4. 运行时 rocBLAS 按形状查表挑最优编号。

本项目的 `STRATA_GEMM_SOL=2560x6144=20377` 里的 **20377 就是一条 Tensile solution 编号**，`rocblas_gemm_ex_get_solutions` 能枚举出 **512 条**候选 —— 这证明我们已经在"成熟库"里挑最优，只是**只挑得到 f16/bf16 那部分**：int8 路径没有可 pin 的成熟 solution 集。

## 两条可执行路线

### 路线 A：用 Tensile 自己生成 int8 solution 集

- 输入：Tensile 工具链 + **gfx928 的 int8 asm 模板**（最大未知数）
- 产出：一批 int8 kernel + 逻辑表，挂进 rocBLAS 句柄
- 与已失败的 `rocblas-gemm-tune` **完全不同**：后者只是在已有库里调参（YAML 打 stdout、需 `Tests:` 包装、15+ 分钟/形状、无 profile 行，工程不可行）；路线 A 是**跑生成器本身**
- 风险：若 gfx928 的 int8 模板缺失，此路直接死在第一步

### 路线 B：借用上游 gfx9 系 int8 逻辑文件后重编

- gfx908/90a 的 MFMA int8 与本平台的 MMAC int8 属同一族指令
- 取上游已编好的 int8 Tensile 逻辑/tile 参数，按 gfx928 的 CU/LDS/VGPR 约束**重编**
- 挂进现有 rocBLAS，然后用**已有的 `STRATA_GEMM_SOL` 机制直接 pin 编号**
- 优点：接口不变，模型侧代码一行不改，回滚方式与现在完全相同

## 分阶段计划（每阶段可独立终止）

| 阶段 | 目标 | 通过判据 | 失败则 |
|---|---|---|---|
| 1 | 单形状 int8 dense GEMM | `N=2560, K=6144` 达 **≥130 TFLOP/s**（int8 峰值 39%）且**引擎内**验证 | 终止，回到 −6.5~−7.1% 现状 |
| 2 | MoE gate/up 接入 | gate/up 阶段（当前 10.7 s）下降 ≥30% | 保留阶段 1 成果 |
| 3 | 全量替换 f16 dense 池 | dense 池（当前 ≈16.6 s）下降 ≥30% | 灰度回滚 |

阶段 1 的 130 TFLOP/s 门槛是从"当前 49 → 需要超过 f16 的 95.6 才有意义"反推的保守值；若达不到，继续投入没有经济性。

## 为什么值得立项

- 硬件已证明能跑 99.8% 峰值，**缺口完全是软件**；
- 一旦 dense 池（27%）+ gate/up（17.5%）换成 int8，端到端有 **20%+ 的空间** —— 这正是当初的立项目标；
- 这部分工作**不需要改前端/服务层**，只在 GEMM 层替换实现，风险面可控。
